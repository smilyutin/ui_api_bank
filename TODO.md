# Test coverage gaps — from README vulnerability audit

Source: coverage audit of `README.md` "Implemented Vulnerabilities" against `tests/api/*.spec.ts` and `tests/ui/specs/*.spec.ts`. Each item below has zero or only superficial test coverage today.

## High priority — real gaps, straightforward to add

- [x] **XSS** — added `fixtures/api/xss.helpers.ts`, `tests/api/xss.spec.ts`, `tests/ui/specs/xss.spec.ts`. Two confirmed, independently-exploitable vectors (AI chat message was checked and is *not* vulnerable — `escapeHtml()` in `static/dashboard.js`):
  - Server-side: `templates/dashboard.html:64` renders `{{ username | safe }}` (Jinja auto-escaping disabled) and `/register` applies no validation to `username` — proven via raw HTTP response text in the API spec.
  - Client-side DOM sink: `static/dashboard.js:279-300` assigns `transaction-list.innerHTML = transactionHtml`, interpolating a transfer's `description` unescaped (self-labeled `// Vulnerability: innerHTML used with unsanitized data` in the source) — proven via real script execution (`<img onerror>` marker) in the UI spec, since an API-only check can't confirm DOM execution.
- [x] **CSRF** — `tests/security/crossSiteReqForgery/csrf.spec.ts`. Confirmed live end-to-end: a cookie-only request (no `Authorization` header) with a foreign `Origin`/`Referer` and no CSRF token completed a real `/transfer` — verified balance actually moved (from $1000 to $990).
- [x] **File upload validation** — `tests/security/input/file-upload.spec.ts`. Of the four sub-items, three are real, one wasn't:
  - [x] unrestricted file type — confirmed, and worse than expected: an uploaded `.html` file is served back with `Content-Type: text/html` + `Content-Disposition: inline`, so it **executes** — a third independent stored-XSS vector alongside `tests/api/xss.spec.ts`/`tests/ui/specs/xss.spec.ts`.
  - [x] path traversal in filename — **checked and NOT exploitable**: `secure_filename()` neutralizes it (confirmed live), contrary to the code's own `# Vulnerability: Path traversal possible` comment.
  - [x] oversized file — confirmed, no size limit enforced (3MB accepted).
  - [x] unsafe/collision-prone file naming — `tests/security/input/file-upload.spec.ts`. `app.py` uses `random.randint(1, 1000000)` (same non-cryptographic `random` module as the reset PIN and card number/CVV generators) as the sole uniqueness guard on top of `secure_filename()`.
- [x] **Predictable virtual card number generation** — `tests/api/virtual-cards.spec.ts`. Turned out not to be "sequential" the way bill-payment references are (`int(time.time())`) — `generate_card_number()`/`generate_cvv()` use `random.choices(string.digits, k=...)`, which produces non-sequential output per-call (confirmed live across 3 samples, no collisions). The real, still-valid finding is the RNG source itself: CWE-330 (non-cryptographic `random` instead of `secrets` for a security-sensitive value), same class as the reset-PIN and file-naming findings above.
- [x] **Rate limiting outside AI chat** — `tests/security/abuse/rate-limit.spec.ts` probes `/login` (bruteforce burst) and `GET /api/bill-categories` (public read burst); both confirmed unthrottled (`@ai_rate_limit` in app.py is wired to exactly 3 AI-chat routes and nowhere else). `/transfer` and `/request_loan` (authenticated endpoints) still uncovered — revisit if extending this further.

## Medium priority — needs a real assertion, not just a smoke test

- [x] **Session expiration** — `tests/security/authentication/session-timeout.spec.ts` + `jwt.spec.ts` confirm a real token's payload has no `exp` claim (verified against a live-issued token) and continues to authenticate `/dashboard` indefinitely. `dashboard.spec.ts`'s toothless UI check (and the now-unused `checkSessionTimeout` page-object helper) has been deleted as superseded.
- [x] **No server-side token invalidation** — `tests/security/authentication/logout-clears-session.spec.ts` confirms there's no `/logout` route at all and the same token still authenticates after "logout". `session-fixation.spec.ts` additionally confirms a pre-password-reset token still works post-reset.
- [x] **No transaction/amount ceiling for `/transfer` and `/request_loan`** — mirrored the bill-payments pattern into both. `/transfer` (`money-transfer.spec.ts`): a $999,999,999 transfer is rejected only for "Insufficient funds" (no independent ceiling). `/request_loan` (`loans.spec.ts`): unlike transfers/bill payments, loans have no balance to check against at all — a $999,999,999 loan request just succeeds outright with no rejection path whatsoever.
- [x] **SQL injection in biller selection** — `bill-payments.spec.ts` ("should not expose a raw database error for malformed biller_id/category_id input"). Corrected from the original premise: neither `biller_id` (parameterized query) nor `category_id` (Flask `<int:>` route converter, confirmed live: a non-integer path segment 404s before the handler runs) allows classic injection. But `biller_id` sending a non-integer value still produces a **raw Postgres type-coercion error returned to the client** (`invalid input syntax for type integer: ... LINE 4: VALUES (1427, ...)`), disclosing internal numeric IDs and exact query structure — a real, different finding (detailed error exposure, API8) than what was originally assumed.

## Low priority / needs a design decision first

- [x] **Weak password reset (3-digit PIN) bruteforce** — `tests/security/authentication/pin-bruteforce.spec.ts`. 20 wrong PIN guesses against `POST /reset-password` all returned 400 (never 429), and the real PIN still worked immediately afterward — confirmed no rate limiting/lockout on the reset flow, matching `app.py`'s own `# Vulnerability: No rate limiting on PIN attempts` comment. Doesn't exhaustively brute the full 900-value space (900 sequential requests wasn't worth it once throttling-absence was already proven with 20). `/forgot-password`'s username-enumeration vector (404 "user not found" vs 200 + PIN) noted but not separately tested — a distinct, smaller finding from the PIN-guessing one.
- [x] **Plaintext password storage** — `tests/security/authentication/plaintext-password-storage.spec.ts` (found during a later coverage pass, not the original audit). `GET /debug/users` is fully unauthenticated and returns every user's password in plaintext — confirmed live by registering a fresh user and finding its exact password in the response, including the seeded admin account (`admin`/`admin123`).
- [x] **Token-in-localStorage as a finding** — `tests/security/authentication/xss-csp-storage.spec.ts` reports it as a finding: the token is duplicated into `localStorage` by `static/dashboard.js` even though `/login` also sets an HttpOnly cookie, so the HttpOnly protection is circumvented by the app's own client code.

## New findings (from mirroring another project's `security/` test-suite layout — not in the original README audit)

- [ ] **Werkzeug interactive debugger exposure** — `tests/security/authentication/broken-authentication.spec.ts` discovered that Flask is running with `DEBUG=True`: the legacy `/api/login` route (still registered via `init_auth_routes(app)` in `app.py`, SQLite-backed, separate from the real Postgres-backed `/login`) throws an unhandled `sqlite3.OperationalError` and returns the full interactive Werkzeug debugger page (file paths, stack frames, library versions). The console itself is PIN-locked (not bypassed/tested — that would cross into actual RCE-adjacent exploitation, deliberately out of scope), but the traceback disclosure alone is a confirmed CRITICAL-adjacent finding. Consider: disabling debug mode for any shared/deployed instance, and/or removing the dead `/api/login`, `/api/check_balance`, `/api/transfer` routes in `auth.py` entirely.
- [x] **CSP header** — confirmed absent everywhere (`tests/security/authentication/xss-csp-storage.spec.ts`); would reduce blast radius of the already-confirmed XSS vectors (`tests/api/xss.spec.ts`, `tests/ui/specs/xss.spec.ts`).
- [x] **Cookie hardening** — `token` cookie is `HttpOnly` but missing `Secure`/`SameSite` (`tests/security/authentication/inspect-cookies.spec.ts`); also usable entirely on its own with no `Authorization` header (`auth.cookies.spec.ts`) — this is exactly the CSRF vector confirmed live in `crossSiteReqForgery/csrf.spec.ts`.
- [ ] **Card/balance race conditions** (virtual cards, bill payments, transfers) — intentionally left uncovered because `app.py` runs single-threaded (documented in code comments in `money-transfer.spec.ts:29` and `bill-payments.spec.ts:41`). Revisit only if the app is ever run with `threaded=True` or behind a real WSGI server.
- [ ] **AI: Direct DB access / role override attacks** — not exploitable against the current `LocalAIAgent` stub (echo-only, per `ai-chat.spec.ts` header comment). Revisit if a real LLM-backed agent is reintroduced.

## README category 7 (Virtual Card Vulnerabilities) — final two items

- [x] **No transaction verification** — `bill-payments.spec.ts` ("should complete a virtual card payment with no CVV or other transaction verification"). A bill payment via virtual card succeeds using only `card_id`; the card's own CVV (known at test time, from creation) is deliberately never sent. Compounds the pre-existing BOLA finding on the same field (`card_id` isn't even checked for ownership) — anyone who can guess/enumerate a `card_id` can both use it cross-account *and* without proving they hold the card.
- [ ] **Lack of card activity monitoring** — not testable via black-box HTTP: this is a logging/observability property (does the app record and alert on card usage patterns?), not a request/response behavior any Playwright assertion can observe. Would need direct access to application/audit logs, which is out of scope for this suite.

## `tests/security/` coverage — status

All categories from the coverage check against the mirrored `security/` layout are now built: `abuse/`, `authentication/`, `authorization/`, `cors/`, `crossSiteReqForgery/`, `headers/`, `input/`, `supply-chain/`. `sec-objects/<category>/<name>.logic.ts` holds shared probe logic per category; `utils/` re-exports `SecurityReporter` and the test-user helpers.

- [x] **CSRF** — `tests/security/crossSiteReqForgery/csrf.spec.ts` (see above).
- [x] **CORS** — `tests/security/cors/cors.spec.ts` — confirmed live: `Access-Control-Allow-Origin` reflects an arbitrary attacker-controlled origin verbatim (not a fixed allowlist), on both a public GET and a state-changing endpoint's preflight. `Access-Control-Allow-Credentials` is not set, so this doesn't currently enable full cross-origin *response reading* — but it's a live misconfiguration one config change away from that, and the request itself still reaches the server regardless (that's what `csrf.spec.ts` demonstrates the consequence of).
- [x] **Security headers** (clickjacking/X-Frame-Options, HSTS, nosniff/X-Content-Type-Options, Permissions-Policy, Referrer-Policy) — `tests/security/headers/{clickjacking,hsts,nosniff,permissions-policy,referrer-policy}.spec.ts`, sharing `sec-objects/headers/security-headers.logic.ts`. All five confirmed absent. CSP itself was already covered separately (`tests/security/authentication/xss-csp-storage.spec.ts`).
  - [x] **Checked across multiple endpoints, not just `/login`** — `buildRepresentativeEndpoints()` now checks a public HTML page (`/login`), a public JSON API (`/api/bill-categories`), and — the highest-value target — the authenticated dashboard (`/dashboard`, via a real token). All 6 header checks (5 headers/ files + CSP) confirmed absence is systemic across all three, not `/login`-specific (also spot-checked `/` and `/static/dashboard.js` manually — same result everywhere).
- [x] **File upload validation** — `tests/security/input/file-upload.spec.ts` (see above — three of four sub-items confirmed real, path traversal confirmed *not* exploitable).
- [x] **Virtual-card-create mass assignment** — `tests/security/authorization/virtual-card-create-mass-assignment.spec.ts` — **checked and NOT vulnerable**: unlike `/register` and the card limit-update endpoint (both of which do generic field-looping), `POST /api/virtual-cards/create` only ever reads `card_limit`/`card_type` by name in `app.py`; `current_balance`, `is_frozen`, `is_active`, `user_id` sent in the request body were all confirmed ignored (verified: stored `balance` was `0`, not the injected `999999`). The TODO item this replaced was itself based on an incorrect assumption from reading the code shape alone — worth remembering not to assume a gap is a real finding without testing it.
- [x] **Dependency/supply-chain scanning** — `tests/security/supply-chain/dependency-security.spec.ts` runs `npm audit --json` against this repo's own `package-lock.json` (no equivalent CI step existed before). Currently clean (0 vulnerabilities). `csp-sri` and `third-party-scripts` are N/A: the app loads exactly one script (`static/dashboard.js`, same-origin) and zero third-party/CDN resources — verified by grepping every `templates/*.html` for `<script src=` and external URLs.
- [x] **Password policy** — `tests/security/authentication/password-policy.spec.ts` (new, from a test-count comparison against another project's suite, not the original README audit). `POST /register` accepts an empty string, `"a"`, `"123"`, and `"password"` with zero length/complexity validation — confirmed live across all four.

## Documentation fix (not a test gap)
